# Agent operating instructions — TheraBridge-Emergent

Applies to Emergent and any future ChatGPT, Codex, Claude or human engineering contributor.

1. **Truth hierarchy:** signed owner decisions in private `NTinkicht/TheraBridge` → owner-provided TheraBridge Emergent blueprint → current implementation. Mark unresolved/unsigned policies as OPEN; do not invent decisions.
2. **Synthetic only:** never use real children, guardian accounts, therapy notes, clinical images, recordings, health records, or live patient data in Emergent.
3. **Portable first:** never let app logic depend on Emergent chat memory. Commit source, tests, schema/migrations, deterministic synthetic seed, dependency locks, runbooks, architecture and permission mappings.
4. **One work unit at a time:** plan → implement → run tests → update evidence files → export GitHub checkpoint → verify SHA → independent reviewer → next task.
5. **Denial by default:** clinical approvals/signatures, guarded releases, consent, safeguarding, sensitive media and recording stay disabled until named owner review and sign-off. Admin rights do not confer clinical access.
6. **Scope checks on the server:** tenant, child, actor relationship, active assignment, role/specialty, consent and version when relevant. Never rely on sidebar hiding.
7. **Keep current:** `docs/handover/CURRENT_STATE.md`, `docs/handover/WORK_LOG.md`, `docs/handover/NEXT_WORK.md`, `docs/qa/TEST_RESULTS.md`; mark PASS/FAIL/NOT RUN accurately.
8. **API and data transparency:** document dependencies, schema, endpoint contracts, rate limits, jobs, externally owned services, environment variable **names only**, and exit strategy.
9. **Prefer the approved stack:** Next.js, React, TS, NestJS/Fastify, PostgreSQL/Prisma, Redis/BullMQ, OIDC, private object store. If Emergent cannot support it, request explicit approval for a clearly segregated prototype; never silently swap architecture.
10. **No secrets in git.** Never force-push or overwrite `main`, never publish a clinical or production application. Autonomous PR merges are allowed **only** under the strict owner-authorized Rule 16 below.
11. **Design:** TheraBridge naming, Direction B brand system, IBM Plex Sans, exact tokens supplied by owner, responsive 320/390/768/1024/1440. Implement a replaceable logo component, no fabricated official emblem.
12. **Takeover test:** prove clean clone → install → seed → start → test → change code on new branch → PR without Emergent; do not claim verified without execution evidence.
13. **Mandatory review-finding disposition (all current and future PRs):** Every reviewer comment (Codex, Mistral, Grok, CodeRabbit, DeepSeek, human, etc.) must receive one explicit evidence-based decision before merge: `FIX_NOW`, `DEFER_ISSUE`, or `DECLINE_WITH_REASON`. Keep a traceable ledger in PR discussion or description linking each suggestion to its comment, code commit, deferred GitHub issue, or reasoned rejection. Non-blocking never means ignored. Inspect all new comments after each review cycle; do not silently leave P3s undecided.
14. **Severity and merge gate:** Fix every applicable P0/P1/P2 finding before merge, with regression tests where appropriate; independently verify the exact final HEAD in all six CI jobs. Fix small, low-risk, scope-aligned P3s immediately, preferably in a consolidated batch before final review. Defer larger P3s or roadmap expansions to a specifically described linked GitHub issue (owner/acceptance conditions/priority when available). Decline suggestions that are redundant, conflict with agreed requirements or introduce disproportionate risk/complexity, with a concise technical justification. Never lower the severity of a real security, data-integrity or privacy flaw merely to defer it.
15. **Review-credit discipline:** Consolidate fixes and worthwhile suggestions before requesting an expensive Codex review, then request only one review per stable, CI-green exact HEAD. Check for an existing pending/completed request at the same SHA/base and do not duplicate it. If the owner explicitly directs changes while Codex is already running, make the requested changes but mark its review SHA outdated and requalify the new HEAD; do not presume an old Codex review covers new commits. Never merge with a blocking unresolved finding, red/incomplete required CI or unsigned clinical governance decisions. See `docs/handover/REVIEW_DISPOSITION_RULE.md` for the checklist.

16. **Owner-authorized autonomous PR merge (effective only after this rule merges to `main`; owner decision 2026-10-31):** Without requesting fresh owner approval for each ordinary synthetic-only development PR, the primary writer may merge an **open, ready-for-review, mergeable** PR only after checking the exact current HEAD and base and recording evidence that all six required CI jobs (`test`, `secret-scan`, `live-session`, `preview-container`, `demo-journey`, `compose`) passed on that HEAD; an independent Codex/approved reviewer completed a review of that same HEAD with no blocking findings; **all** top-level and inline comments from **every** reviewer, including later re-reviews, have a traceable `FIX_NOW`, `DEFER_ISSUE`, or `DECLINE_WITH_REASON` disposition; every applicable P0–P2 is fixed and tested (or demonstrably false with independent evidence); all actionable low-risk P3s are fixed; each deferred non-blocking finding has a linked GitHub issue specifying rationale, acceptance criteria, priority, responsible owner/next action and safety boundary; declined findings have technical reasons; and no unresolved blocking thread, stale review, failing or pending check, conflict, or required policy gate remains. **A positive review alone or an issue link without explicit disposition is never sufficient.** If HEAD/base changes, requalify. Once all checks are satisfied, merge and report the merge SHA without a new approval prompt. If the PR changes clinical activation, real data processing, authorization/consent/signing/release/safeguarding policy, production deployment, published migration identity/history, or other separately signed/owner-gated decisions, **stop and obtain the necessary explicit owner authorization**; green CI does not override governance. Never automatically merge a draft, bypass protections, force-push, or activate a deployment. See `docs/handover/REVIEW_DISPOSITION_RULE.md` for the merge checklist.
